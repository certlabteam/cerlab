    CSRF에 대한 설명으로 옳은 것은?

    1. 1. 취약한 컴포넌트를 악용하여 공격하면 데이터 손실이나 서버 장악 문제가 발생할 수 있는 취약점이다.
    2. 2. 조작된 XPath(XML Path Language) 쿼리를 보냄으로써 비정상적인 데이터를 쿼리를 이용해 가져올 수 있는 취약점이다.
    3. 3. 적절히 보호되지 않은 쿠키를 사용하여, 쿠키 값 변조를 통한 다른 사용자로의 위장 및 권한 상승 등이 가능한 취약점이다.
    4. 4. 로그인한 사용자 브라우저로 하여금 사용자의 세션 쿠키와 기타 인증 정보를 포함하는 위조된 HTTP 요청을 전송할 수 있는 취약점이다.

    정답 4번

    🔍 보기별 해설
    1. 취약한 컴포넌트를 악용해 데이터 손실이나 서버 장악까지 이어지는 것은 알려진 취약점이 있는 구성요소를 쓰는 문제에 대한 설명이라 CSRF와는 다르므로 이 답은 옳지 않다.
    2. 조작된 XPath 쿼리로 비정상 데이터를 가져오는 것은 XPath 인젝션에 대한 설명이라 CSRF와는 다르므로 이 답은 옳지 않다.
    3. 제대로 보호되지 않은 쿠키를 변조해 다른 사용자로 위장하는 것은 쿠키 취약점에 대한 설명이라 CSRF와는 다르므로 이 답은 옳지 않다.
    4. CSRF는 로그인해 둔 사용자의 브라우저가 자신도 모르는 사이에 세션 쿠키와 인증 정보를 실은 위조된 요청을 공격자가 원하는 대로 서버에 보내게 만드는 취약점이므로 이 답이 옳다(정답).
    🧮 풀이
    1. 甲은 오래된 버전의 라이브러리를 그대로 쓰던 서버가 알려진 취약점을 통해 통째로 장악당한 사고 사례를 조사해 보았다. 취약한 컴포넌트 문제라는 것을 확인하고 CSRF와는 다른 사례로 분류했다.
    2. 甲은 XML 데이터베이스에 조작된 XPath 쿼리를 보내 원래는 볼 수 없던 항목까지 조회되는지 시험해 보았다. 이 취약점도 CSRF와는 다른 갈래라는 것을 정리했다.
    3. 甲은 보호되지 않은 쿠키 값을 다른 사용자의 값으로 바꿔치기해 그 사람인 척 접속해 보았다. 쿠키 자체를 훔쳐 위장하는 방식이라 CSRF와는 다르다는 것을 확인했다.
    4. 甲은 로그인해 둔 사용자가 악성 링크를 클릭하자 그 사람의 브라우저가 본인도 모르게 계좌이체 요청을 서버에 보내는 것을 재현해 보았다. 세션 쿠키가 자동으로 함께 실려 가는 것을 패킷으로 확인하고 CSRF 취약점으로 기록했다.

    로그인한 사용자 브라우저가 위조된 요청을 대신 보내게 만드는 것이 CSRF이므로 4번이 정답이다.

    다음에서 설명하는 검사 도구는?

    어느 한 시점에서 시스템에 존재하는 특정 경로 혹은 모든 파일에 관한 정보를 DB화하여 저장한 후, 수정ㆍ삭제ㆍ생성된 파일에 관한 정보를 알려주며, 해커들에 의한 파일의 위변조 여부를 판별할 수 있는 기능을 제공해 주는 검사 도구이다.

    1. 1. Tripwire
    2. 2. Burp Suite
    3. 3. Snort
    4. 4. NESSUS

    정답 1번

    🔍 보기별 해설
    1. Tripwire는 한 시점의 파일 정보를 데이터베이스로 만들어 두고 그 뒤 수정·삭제·생성된 파일을 찾아내 위변조 여부를 알려 주는 무결성 검사 도구이므로 이 답이 옳다(정답).
    2. Burp Suite는 웹 요청과 응답을 가로채 조작해 보며 취약점을 찾는 프록시 도구라 파일 정보를 DB화하는 것과는 다르므로 이 답은 옳지 않다.
    3. Snort는 네트워크를 오가는 패킷을 실시간으로 감시해 침입 시도를 탐지하는 도구라 파일 위변조를 찾는 것과는 다르므로 이 답은 옳지 않다.
    4. NESSUS는 시스템에 알려진 취약점이 있는지 스캔해 목록으로 보여 주는 도구라 파일 정보를 DB화해 위변조를 찾는 것과는 다르므로 이 답은 옳지 않다.
    🧮 풀이
    1. 甲은 서버의 중요 파일들을 Tripwire로 한 번 스캔해 해시값을 데이터베이스에 저장해 두었다. 며칠 뒤 다시 스캔했을 때 바뀐 파일 하나가 알림으로 뜨는 것을 확인했다.
    2. 甲은 Burp Suite로 로그인 요청을 가로채 파라미터 값을 조작해 서버 반응을 살펴보았다. 이 도구는 파일 위변조가 아니라 요청 자체를 조작하는 데 쓰인다는 것을 정리했다.
    3. 甲은 Snort를 돌려 놓고 외부에서 들어오는 수상한 패킷 패턴이 있는지 실시간으로 지켜보았다. 이 도구 역시 파일 정보를 DB화하는 것과는 다른 방식이라는 것을 확인했다.
    4. 甲은 NESSUS로 서버를 스캔해 패치되지 않은 알려진 취약점 목록을 뽑아 보았다. 이 도구도 파일의 변경 여부를 추적하는 것과는 다른 목적이라는 것을 정리했다.

    파일 정보를 DB화해 위변조 여부를 알려주는 검사 도구는 Tripwire이므로 1번이 정답이다.

    robots.txt 파일에 대한 설명으로 옳은 것은?

    1. 1. robots.txt 파일은 웹 루트 디렉터리에 위치한다.
    2. 2. User-agent는 접근거부 디렉터리를 나타내는 키워드이다.
    3. 3. Disallow는 검색 엔진 종류를 나타내는 키워드이다.
    4. 4. User-agent와 Disallow는 동시에 사용할 수 없다.

    정답 1번

    🔍 보기별 해설
    1. robots.txt 파일은 검색엔진 로봇이 가장 먼저 찾아보도록 웹사이트의 루트 디렉터리에 놓이는 것이 표준 규칙이므로 이 답이 옳다(정답).
    2. User-agent는 접근거부 디렉터리를 나타내는 것이 아니라 어떤 검색엔진 로봇을 대상으로 하는지 지정하는 키워드이므로 이 답은 옳지 않다.
    3. Disallow는 검색엔진 종류를 나타내는 것이 아니라 접근을 막을 디렉터리나 경로를 지정하는 키워드이므로 이 답은 옳지 않다.
    4. User-agent와 Disallow는 짝을 이뤄 함께 쓰이는 키워드라 동시에 쓸 수 없다는 것은 실제 사용법과 어긋나므로 이 답은 옳지 않다.
    🧮 풀이
    1. 甲은 어느 사이트의 robots.txt 주소를 도메인 바로 뒤에 붙여 접속해 내용을 확인해 보았다. 하위 폴더가 아니라 루트 경로에 그대로 파일이 놓여 있는 것을 확인했다.
    2. 甲은 User-agent 자리에 특정 검색엔진 이름을 적어 그 로봇에게만 규칙을 적용해 보았다. 그 키워드가 접근거부 경로가 아니라 대상 로봇을 가리키는 것을 확인했다.
    3. 甲은 Disallow 자리에 접근을 막고 싶은 폴더 경로를 적어 검색엔진이 그 폴더를 건너뛰는지 확인해 보았다. 그 키워드가 검색엔진 종류가 아니라 경로를 가리키는 것을 확인했다.
    4. 甲은 robots.txt 파일에 User-agent와 Disallow를 한 쌍으로 나란히 적어 특정 로봇의 특정 경로 접근을 막아 보았다. 두 키워드가 함께 쓰이는 것을 실제 파일로 확인했다.

    robots.txt 파일은 웹 루트 디렉터리에 놓이므로 1번이 정답이다.

    다음은 Windows 운영체제가 설치된 시스템에서 SID를 출력한 결과이다. (가), (나)에 대한 설명으로 옳지 않은 것은?

    1. 1. (가)는 시스템 부팅 시마다 새롭게 부여되는 시스템 ID이다.
    2. 2. (나)는 RID를 나타내며, 500의 경우 Administrator임을 의미한다.
    3. 3. (나)는 RID를 나타내며, 501의 경우 Guest임을 의미한다.
    4. 4. (나)는 RID를 나타내며, 일반 사용자에게는 1,000 이상의 숫자가 부여된다.

    정답 1번

    🔍 보기별 해설
    1. (가)는 시스템을 설치할 때 한 번 생성돼 고정되는 도메인·컴퓨터 식별자이지 부팅할 때마다 새로 부여되는 값이 아니므로 이 설명은 옳지 않다(정답).
    2. (나)가 RID를 나타내며 500이면 Administrator를 가리킨다는 것은 윈도 SID 체계 그대로이므로 이 설명은 옳다.
    3. (나)가 RID를 나타내며 501이면 Guest를 가리킨다는 것은 윈도 SID 체계 그대로이므로 이 설명은 옳다.
    4. (나)가 RID를 나타내며 일반 사용자에게는 1,000 이상의 숫자가 부여된다는 것은 윈도 SID 체계 그대로이므로 이 설명은 옳다.
    🧮 풀이
    1. 甲은 같은 컴퓨터를 여러 번 재부팅한 뒤 SID의 (가) 부분을 whoami 명령으로 매번 확인해 보았다. 재부팅해도 그 값이 한 번도 안 바뀌고 그대로인 것을 확인했다.
    2. 甲은 관리자 계정의 SID 끝자리를 확인해 500이라는 RID가 찍혀 있는 것을 보았다. 그 값이 Administrator를 가리킨다는 것을 문서와 대조해 확인했다.
    3. 甲은 사내 보안교육 자료에서 손님용 계정으로 로그인하면 RID가 501번으로 고정된다는 설명을 읽고 실습용 게스트 계정으로 직접 로그인해 보았다. 화면에 뜬 권한 정보가 자료 설명과 그대로 맞는 것을 확인했다.
    4. 甲은 새로 만든 일반 사용자 계정 여러 개의 SID 끝자리를 차례로 확인해 1,000번대 이상의 숫자가 붙는 것을 확인했다. 관리자·게스트와는 다른 번호대가 매겨지는 것을 정리했다.

    (가) 도메인 식별자는 설치 시 한 번 정해지고 부팅마다 안 바뀌는데 지문이 매번 새로 부여된다고 해 1번이 옳지 않다.

    디지털 포렌식의 절차에서 사전준비 이후 단계를 순서대로 바르게 나열한 것은?

    (가) 증거 수집 (나) 보관 및 이송 (다) 보고서 작성 (라) 증거 분석 및 조사

    1. 1. (가) → (나) → (다) → (라)
    2. 2. (가) → (나) → (라) → (다)
    3. 3. (나) → (가) → (다) → (라)
    4. 4. (나) → (라) → (가) → (다)

    정답 2번

    🔍 보기별 해설
    1. 증거 수집 다음에 보관 및 이송을 놓은 것은 맞지만 그다음에 보고서 작성을 먼저 놓으면 아직 분석도 하지 않은 채 보고서부터 쓰는 셈이라 이 순서는 옳지 않다.
    2. 증거를 먼저 수집하고 보관·이송한 뒤 그 증거를 분석·조사하고 마지막으로 보고서를 작성하는 것이 디지털 포렌식의 실제 절차 순서이므로 이 순서가 옳다(정답).
    3. 보관 및 이송을 증거 수집보다 앞에 놓으면 아직 모으지도 않은 증거를 먼저 옮긴다는 셈이라 이 순서는 옳지 않다.
    4. 보관 및 이송, 분석 및 조사를 증거 수집보다 앞에 놓으면 역시 모으지도 않은 증거를 먼저 옮기고 분석한다는 셈이라 이 순서는 옳지 않다.
    🧮 풀이
    1. 甲은 증거를 수집하고 옮긴 바로 다음 단계로 보고서부터 작성하려다 아직 분석을 하지 않았다는 것을 뒤늦게 알아차렸다. 분석 단계를 보고서 작성보다 앞에 끼워 넣어 순서를 고쳤다.
    2. 甲은 현장에서 하드디스크를 압수해 봉인하고 증거보관소로 옮긴 뒤 그 디스크를 분석실에서 하나하나 조사해 보았다. 조사 결과를 정리해 마지막으로 보고서를 작성했다.
    3. 甲은 아직 증거를 압수하지도 않은 상태에서 보관 절차부터 먼저 밟으려다 순서가 뒤바뀐 것을 뒤늦게 확인했다. 증거 수집을 맨 앞으로 옮겨 순서를 다시 바로잡았다.
    4. 甲은 보관과 분석 단계를 증거 수집보다 앞에 놓고 절차서를 처음부터 새로 작성해 보았다. 실제로는 수집이 모든 절차의 출발점이라는 것을 다시 확인해 순서를 고쳐 적었다.

    사전준비 뒤 증거수집→보관및이송→증거분석및조사→보고서작성 순서인 2번이 정답이다.

    (가), (나)에 들어갈 용어를 바르게 연결한 것은?

    ○ CVE(Common Vulnerabilities and Exposure)는 공개적으로 알려진 소프트웨어의 보안취약점을 가리키는 고유 표기를 의미한다.

    ○ 취약점명은 CVE－ (가) － (나) 형식으로 구성되어 있다. (가) (나)

    1. 1. 일련번호 소프트웨어 버전
    2. 2. 연도 소프트웨어 버전
    3. 3. 일련번호 연도
    4. 4. 연도 일련번호

    정답 4번

    🔍 보기별 해설
    1. 일련번호와 소프트웨어 버전 순서로 적으면 CVE 번호에는 애초에 소프트웨어 버전이 들어가지 않으므로 이 조합은 옳지 않다.

    3. 수신자가 그 값을 송신자의 공개키로 복호화해 해시코드를 되찾는다는 것은 PGP 인증 절차 그대로이므로 이 설명은 옳다.
    4. PGP는 서명을 만드는 데 RSA뿐 아니라 DSS도 함께 쓸 수 있도록 허용하는데 지문은 DSS를 허용하지 않는다고 거꾸로 말하니 이 설명은 옳지 않다(정답).

    2. 甲은 앞서 구한 해시코드를 자신의 개인키로 암호화해 메일 본문 뒤에 덧붙여 발송해 보았다. 수신자가 그 값을 보고 서명이 붙은 메일임을 알아차리는 것을 확인했다.
    3. 甲은 수신한 서명 메일에서 암호화된 해시코드를 송신자의 공개키로 복호화해 원래 해시코드를 되찾아 보았다. 그 값이 자신이 계산한 메시지 해시코드와 일치하는 것을 확인했다.

    다음에서 설명하는 웹 취약점은?

    웹 애플리케이션을 구동하는 웹 서버의 보안 설정이 취약하여 발생하는 보안 설정 오류 취약점이다. 정상적인 URL 경로 중 확인 대상 디렉터리까지만 직접 접근하여 이 취약점을 점검할 수 있다.

    2. 2. 디렉터리 인덱싱

    4. XSS는 사용자 입력에 스크립트를 끼워 넣어 다른 사용자 브라우저에서 실행시키는 공격이라 디렉터리 경로 접근 점검과는 다르므로 이 답은 옳지 않다.

    3. 甲은 로그인 입력창 옆의 검색창에도 시스템 명령을 함께 끼워 넣어 서버 반응을 비교해 보았다. 이 방식도 디렉터리 경로를 열람하는 점검과는 전혀 다른 갈래라는 것을 정리했다.
    4. 甲은 게시판 입력창에 경고창을 띄우는 스크립트를 넣어 그 글을 다시 열었을 때 실행되는지 확인해 보았다. 이 방식 역시 디렉터리 접근 점검과는 다른 취약점이라는 것을 정리했다.

    다음 리눅스 시스템 사용자 패스워드 저장 과정의 (가) ～ (다)에 들어갈 내용을 바르게 연결한 것은?

    (가) (나) (다)

    1. 1. Salt RSA /etc/passwd
    2. 2. Salt SHA256 /etc/shadow
    3. 3. 암호키 MD5 /etc/passwd
    4. 4. 암호키 ARIA /etc/shadow

    정답 2번

    🔍 보기별 해설
    1. 패스워드에 더하는 값을 RSA로, 저장 파일을 /etc/passwd로 적으면 RSA는 암호화 알고리즘이지 더해 주는 임의값이 아니고 저장 위치도 실제로는 shadow 파일이라 이 조합은 옳지 않다.
    2. 사용자 패스워드에 Salt라는 임의값을 더한 뒤 SHA256 같은 해시함수로 뒤섞어 암호화된 패스워드를 만들고 그 값을 관리자만 읽을 수 있는 /etc/shadow 파일에 저장하므로 이 조합이 옳다(정답).

    🧮 풀이
    1. 甲은 같은 패스워드를 쓰는 두 계정의 저장값이 RSA로 암호화됐다고 가정하고 비교해 보려다 실제로는 Salt를 더해 해시하는 방식이라는 것을 다시 확인했다. 저장 위치도 passwd가 아니라 shadow라는 것을 함께 확인했다.
    2. 甲은 새 계정을 만들며 패스워드에 무작위 Salt 값이 더해지고 SHA256 해시함수를 거쳐 암호화되는 과정을 로그로 지켜보았다. 완성된 값이 shadow 파일에 저장되는 것을 확인했다.
    3. 甲은 저장 방식을 암호키와 MD5, passwd 파일 조합으로 잘못 짐작해 표를 만들어 보았다. 실제 표준 문서를 다시 찾아 세 자리 모두 다른 값이라는 것을 확인하고 표를 고쳤다.
    4. 甲은 더해지는 값을 암호키라 적고 해시함수를 ARIA로 적어 표를 만들어 보았다. 실제로 더해지는 것은 Salt이고 널리 쓰이는 해시함수는 SHA 계열이라는 것을 다시 확인했다.

    x86 32bit 계열 CPU의 레지스터에 대한 설명으로 옳지 않은 것은?

    3. RSA 키 발생기는 TPM 안에서 공개키 암호화에 쓸 키 쌍을 만들어 내는 실제 구성요소이므로 이 설명은 옳다.

    1. 甲은 TPM 칩이 암호화 키를 만들 때 쓰는 난수 값을 여러 번 뽑아 매번 다른 값이 나오는 것을 확인해 보았다. 그 난수 발생기가 TPM 내부 구성요소라는 것을 정리했다.
    2. 甲은 TPM 안의 암복호화 엔진이 데이터를 직접 암호화해 밖으로 내보내는 과정을 여러 번 반복해 시험해 보았다. 소프트웨어가 아니라 칩 안에서 처리되는 것을 확인했다.
    3. 甲은 TPM이 RSA 키 쌍을 새로 만들어 내는 과정을 관리도구 화면으로 천천히 지켜보았다. 그 키가 외부로 유출되지 않고 칩 안에 안전하게 보관되는 것을 확인했다.
    4. 甲은 TPM 사양서를 뒤져 MD5 해시 엔진이 표준 구성요소로 실려 있는지 찾아보았다. 실제로는 SHA-1 계열 엔진이 표준으로 쓰이고 MD5는 실려 있지 않다는 것을 확인했다.

    TPM 표준 구성요소는 SHA-1 계열이라 MD5 해시값 생성기는 해당하지 않아 4번이 정답이다.

    다음에서 설명하는 공격은?

    소유자가 root이고 SetUID 비트를 가진 프로세스가 생성한 임시 파일의 처리가 완료되기 전에 공격자의 프로세스가 동일한 이름의 심볼릭 링크 파일을 생성하여 root 소유의 파일 내용을 수정하는 공격 기법이다.

    2. 2. Format String
    3. 3. Heap Overflow
    4. 4. Stack Overflow

    정답 1번

    🔍 보기별 해설
    1. Race Condition은 root 소유의 SetUID 프로세스가 임시파일을 처리하는 그 짧은 틈을 노려 공격자가 같은 이름의 심볼릭 링크를 걸어 root 권한으로 엉뚱한 파일을 수정하게 만드는 공격이므로 이 답이 옳다(정답).
    2. Format String은 서식 문자열 자리에 사용자 입력을 그대로 넣어 메모리 값을 읽거나 쓰는 공격이라 임시파일 처리 시점의 틈을 노리는 방식과는 다르므로 이 답은 옳지 않다.
    3. Heap Overflow는 동적으로 할당된 힙 메모리 영역에 정해진 크기보다 많은 데이터를 밀어 넣어 인접 영역을 덮어쓰는 공격이라 파일 처리 시점의 틈을 노리는 방식과는 다르므로 이 답은 옳지 않다.
    4. Stack Overflow는 스택 영역에 정해진 크기보다 많은 데이터를 밀어 넣어 반환 주소 같은 인접 값을 덮어쓰는 공격이라 파일 처리 시점의 틈을 노리는 방식과는 다르므로 이 답은 옳지 않다.
    🧮 풀이
    1. 甲은 root 권한으로 도는 SetUID 프로그램이 임시파일을 만들고 처리하는 그 짧은 순간을 노려 같은 이름의 심볼릭 링크를 미리 걸어 두었다. 그 프로그램이 링크를 따라가 엉뚱한 root 소유 파일을 고쳐 쓰는 것을 확인하고 레이스 컨디션 공격으로 기록했다.
    2. 甲은 프로그램의 서식 문자열 입력 자리에 %n 같은 지정자를 넣어 메모리 값이 몰래 바뀌는지 시험해 보았다. 이 공격은 임시파일 처리 시점의 틈과는 무관한 갈래라는 것을 정리했다.
    3. 甲은 힙에 할당된 버퍼보다 훨씬 긴 데이터를 밀어 넣어 인접한 힙 영역이 깨지는지 시험해 보았다. 이 공격도 파일 처리 타이밍을 노리는 것과는 다른 방식이라는 것을 정리했다.
    4. 甲은 이번엔 데이터의 길이 자체는 정상이지만 형태 지정자를 조작해 스택에 놓인 값을 몰래 읽어내는 시도를 해 보았다. 이 공격 역시 임시파일 처리 시점의 틈을 노리는 것과는 다른 갈래라는 것을 정리했다.

    SetUID 임시파일 처리 전에 같은 이름 심볼릭링크로 끼어드는 공격은 레이스 컨디션이므로 1번이 정답이다.

    리눅스에서 파일 시스템의 상태를 점검하고, 문제가 있을 때 복구하는 기능을 가진 명령어는?

    1. 1. fdisk
    2. 2. df
    3. 3. fsck
    4. 4. fstab

    정답 3번

    🔍 보기별 해설
    1. fdisk는 디스크를 파티션으로 나누는 명령어라 파일시스템 오류를 점검하고 복구하는 기능과는 다르므로 이 답은 옳지 않다.
    2. df는 디스크의 남은 용량을 보여 주는 명령어라 파일시스템 오류를 점검하고 복구하는 기능과는 다르므로 이 답은 옳지 않다.
    3. fsck는 파일시스템의 상태를 점검해 문제가 있으면 그 자리에서 복구까지 시도하는 명령어이므로 이 답이 옳다(정답).
    4. fstab은 부팅 시 자동으로 마운트할 파일시스템 목록을 적어 둔 설정 파일이라 오류를 점검하고 복구하는 명령어 자체가 아니므로 이 답은 옳지 않다.
    🧮 풀이
    1. 甲은 새 디스크를 여러 파티션으로 나누려 fdisk를 실행해 파티션 테이블을 직접 작성해 보았다. 이 명령이 오류를 복구하는 것과는 다른 목적이라는 것을 정리했다.
    2. 甲은 디스크 용량이 부족해질까 걱정돼 df 명령으로 남은 공간을 하나하나 꼼꼼히 확인해 보았다. 이 명령 역시 파일시스템 오류 복구와는 다른 목적이라는 것을 정리했다.
    3. 甲은 비정상 종료된 서버를 재부팅하며 fsck가 자동으로 파일시스템을 점검하는 과정을 처음부터 지켜보았다. 깨진 블록 하나를 찾아 스스로 복구하는 것을 로그로 확인했다.
    4. 甲은 새 파티션이 부팅 때마다 저절로 마운트되도록 그 목록을 fstab 파일 맨 아래에 한 줄 추가해 보았다. 이 파일 자체는 오류를 점검하거나 복구하는 명령어가 아니라 마운트 설정 목록일 뿐이라는 것을 정리했다.

    파일시스템 점검·복구 기능을 가진 명령어는 fsck이므로 3번이 정답이다.
