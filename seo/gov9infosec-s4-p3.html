    Land 공격을 위한 IPv4 데이터그램 헤더에서 같은 값을 저장하는 필드로만 묶인 것은?

    1. 1. (가), (나)
    2. 2. (다), (라)
    3. 3. (마), (바)
    4. 4. (사), (아)

    정답 4번

    🔍 보기별 해설
    1. (가)와 (나)는 IP 버전과 헤더 길이를 적는 자리라 값이 서로 다를 수밖에 없고 공격과도 관계가 없으므로 옳지 않다.
    2. (다)와 (라)는 데이터그램 전체 길이와 조각 식별자로, 뜻도 쓰임도 달라 같은 값을 넣을 자리가 아니므로 옳지 않다.
    3. (마)와 (바)는 패킷 수명과 상위 프로토콜 번호를 적는 자리라 서로 값을 맞출 까닭이 전혀 없으므로 옳지 않다.
    4. (사)와 (아)는 출발지와 목적지 주소이고 이 둘을 같게 만들어 자기 자신에게 응답하게 하는 것이 Land 공격이므로 옳다(정답).
    🧮 풀이
    1. 甲이 헤더 앞머리의 버전과 길이 값을 억지로 같게 맞춰 보내자, 수신 장비가 헤더 구조를 해석하지 못한다며 패킷을 그대로 버렸고 대상 서버에는 아무 부담도 가지 않았다.
    2. 甲이 전체 길이와 조각 식별자에 같은 수를 넣어 보냈더니 받는 쪽에서 조각 모으기만 어그러졌을 뿐, 대상 장비의 연결 자원은 전혀 소모되지 않아 공격이라 할 것이 없었다.
    3. 甲이 패킷 수명과 프로토콜 번호를 같은 값으로 맞춰 보내자 중간 라우터가 알 수 없는 프로토콜이라며 패킷을 흘려보냈고, 목적지 서버는 그것을 받아 보지도 못했다.
    4. 甲이 출발지와 목적지를 모두 대상 서버 주소로 채워 보내자 서버가 자기 자신에게 응답을 되돌리며 같은 연결 처리에 계속 매달렸고, 그동안 정상 사용자의 요청이 뒤로 밀렸다.

    Land 공격은 출발지 주소와 목적지 주소를 같게 만들어 대상이 자기 자신에게 응답하게 하는 공격이다.

    다음에서 설명하는 취약점을 이용하는 서비스 거부 공격은?

    서버는 클라이언트와 TCP 3-way 핸드셰이크(handshake) 과정을 완료하기 전에 절반－개방(half-open) 연결을 큐에 저장하는데 이 같은 큐는 한정된 용량을 가진다.

    1. 1. Smurf 공격
    2. 2. Teardrop 공격
    3. 3. SYN flooding 공격
    4. 4. Ping-of-death 공격

    정답 3번

    🔍 보기별 해설
    1. Smurf(스머프)는 위조한 송신지 주소와 브로드캐스트를 이용해 응답을 증폭시키는 공격으로 절반 개방 연결 큐와는 다르므로 옳지 않다.
    2. Teardrop(티어드롭)은 조각난 IP(인터넷 프로토콜) 패킷의 오프셋을 조작해 재조합 오류를 일으키는 공격이므로 옳지 않다.
    3. SYN(동기화) flooding(대량 전송)은 연결 완료 전의 절반 개방 상태를 대량 생성해 서버의 대기 큐를 소진시키므로 옳다(정답).
    4. Ping-of-death(비정상 대형 핑)는 허용 범위를 넘는 IP(인터넷 프로토콜) 패킷 재조합을 악용하므로 절반 개방 큐와는 다르므로 옳지 않다.
    🧮 풀이
    1. 甲이 공격 대상의 주소를 출발지로 위조한 ICMP(인터넷 제어 메시지 프로토콜) 요청을 브로드캐스트 주소로 보냈다. 여러 호스트의 응답이 한꺼번에 피해 서버로 몰려들었다.
    2. 甲이 조각난 IP(인터넷 프로토콜) 패킷들의 위치 정보를 서로 겹치게 조작해 서버로 보냈다. 서버가 조각을 다시 맞추는 과정에서 비정상적인 재조합 오류가 발생했다.
    3. 甲이 수많은 SYN(동기화) 요청을 보내고 마지막 확인 응답은 보내지 않았다. 서버의 절반 개방 연결이 대기 큐를 가득 채우면서 정상 사용자의 새 연결 요청이 밀려났다.
    4. 甲이 재조합 결과가 허용된 최대 크기를 넘도록 조각난 ICMP(인터넷 제어 메시지 프로토콜) 패킷을 보냈다. 대상 시스템은 비정상적으로 큰 패킷을 처리하다 오류를 일으켰다.

    SYN(동기화) flooding(대량 전송)은 미완성 연결을 계속 쌓아 절반 개방 연결 큐의 한정된 공간을 소진시키는 서비스 거부 공격이다.

    다음 Go-Back-N ARQ(Automatic Repeat reQuest)를 사용하는 송신기기와 수신기기 사이에 주고받은 통신 패킷 중 (가), (나)에 들어갈 내용을 바르게 연결한 것은? (단, 윈도 크기는 3이다)

    (가) (나)

    1. 1. P0 P1
    2. 2. P1 P2
    3. 3. P2 P3
    4. 4. P3 P4

    정답 3번

    🔍 보기별 해설
    1. P0과 P1은 이미 확인응답으로 정상 수신이 확인된 패킷이어서 재전송 대상에서 제외되며 오류가 발생한 번호부터 다시 보내야 하므로 옳지 않다.
    2. P1은 ACK(확인응답)1로 수신 확인이 끝났고 재전송은 오류가 발생한 P2부터 시작하여 이후 패킷도 함께 다시 보내야 하므로 옳지 않다.
    3. Go-Back-N(고백엔)은 오류가 난 번호부터 되돌아가 연속해서 다시 보내므로 P2와 수신 측이 폐기한 P3을 차례대로 재전송하는 것이 맞아 옳다(정답).
    4. P3부터 다시 보내면 정작 오류가 발생해 정상 수신되지 않은 P2가 빠지고 수신 측의 기대 순서도 충족하지 못해 이후 전송을 이어갈 수 없으므로 옳지 않다.
    🧮 풀이
    1. 甲이 전송 기록을 살피며 이미 ACK(확인응답)0을 받은 P0을 다시 보내려 하자 선배가 정상 수신된 번호에는 표시를 해 두라고 했다. 甲은 확인이 끝난 패킷을 재전송 목록에서 지우고 오류 지점을 다시 찾았다.
    2. 甲이 ACK(확인응답)1까지 받은 것을 확인하고도 P1을 재전송 목록에 넣었다가 수신 기록을 다시 펼쳐 보았다. 확인이 끝난 번호는 빼고 오류가 난 P2부터 잡아야 한다는 것을 확인해 목록을 바로 고쳤다.
    3. 甲이 NAK(부정 확인응답)2를 받은 뒤 P2부터 차례로 다시 보내자 수신 쪽이 앞서 폐기했던 P3도 이어서 받아들였다. 빠졌던 순서가 모두 채워지면서 수신 창이 정상 위치로 이동하고 통신도 계속됐다.
    4. 甲이 P2를 건너뛰고 P3부터 다시 보내자 수신 쪽은 기대하던 P2가 오지 않아 다음 패킷을 받아들이지 않았다. 甲이 뒤이어 여러 패킷을 전송했지만 계속 폐기되어 전송 절차가 더 진행되지 않았다.

    Go-Back-N ARQ는 오류가 난 번호부터 되돌아가 다시 보내므로 NAK2 뒤에는 P2와 P3가 차례로 재전송된다.

    SSL/TLS 프로토콜 구조에 속하지 않는 것은?

    1. 1. Record Protocol
    2. 2. Handshake Protocol
    3. 3. Change Cipher Spec Protocol
    4. 4. Authentication Header Protocol

    정답 4번

    🔍 보기별 해설
    1. Record Protocol은 상위 계층 데이터를 분할하고 암호화와 무결성 보호 등을 적용하여 전송하는 프로토콜이므로 SSL/TLS 프로토콜 구조에 해당한다.
    2. Handshake Protocol은 상대를 인증하고 암호 알고리즘과 키 관련 정보를 협상하여 보안 연결을 설정하므로 SSL/TLS 프로토콜 구조에 해당한다.
    3. Change Cipher Spec Protocol은 협상된 암호 명세를 이후 통신에 적용하도록 상태 변경을 알리므로 SSL/TLS 프로토콜 구조에 해당한다.
    4. Authentication Header Protocol은 IP 패킷의 무결성과 출처 인증을 제공하는 IPSec의 AH이므로 SSL/TLS 프로토콜 구조에 해당하지 않는다(정답).
    🧮 풀이
    1. 甲이 TLS 연결을 통해 큰 업무 데이터를 서버로 전송하자 Record Protocol이 상위 계층에서 받은 데이터를 여러 조각으로 나누었다. 각 조각에 필요한 보호 처리를 적용해 레코드로 만든 뒤 상대 서버로 차례로 보내 안전한 데이터 전송을 이어 갔다.
    2. 甲이 처음 HTTPS 서버에 접속하자 Handshake Protocol을 통해 서버가 제시한 인증서를 확인했다. 이어 양쪽이 사용할 암호 그룹과 키 관련 정보를 서로 협상하고 필요한 값을 교환한 뒤 실제 암호화 통신을 시작할 보안 연결을 마련했다.
    3. 甲이 TLS 핸드셰이크에서 암호 알고리즘과 키 관련 협상을 모두 마친 뒤 Change Cipher Spec 메시지를 전송했다. 상대방이 이를 받은 이후부터 새로 협상된 암호 명세가 적용된 레코드가 오가기 시작해 보호된 통신이 이어졌다.
    4. 甲이 두 지점 사이의 IP 패킷을 보호하려고 IPSec의 AH를 설정하자 각 패킷에 Authentication Header가 추가되었다. 장비는 이를 이용해 패킷의 출처와 무결성을 검사했고, 웹 통신에서 사용하는 TLS 프로토콜과는 별도로 동작했다.

    SSL/TLS 구조에는 Record·Handshake·Change Cipher Spec이 해당하며 Authentication Header는 IPSec의 프로토콜이다.

    암호학적 해시 함수(cryptographic hash function)의 성질 또는 특징으로 옳지 않은 것은?

    1. 1. 양방향성
    2. 2. 충돌 저항성(resistance)
    3. 3. 역상(preimage) 저항성
    4. 4. 제2(second) 역상 저항성

    정답 1번

    🔍 보기별 해설
    1. 암호학적 해시 함수는 입력에서 해시값 계산은 쉬워도 해시값에서 원문을 되찾기 어려운 일방향 함수이므로 양방향성은 특징이 아니어서 옳지 않다(정답).
    2. 충돌 저항성은 서로 다른 두 입력이 같은 해시값을 갖는 쌍을 현실적으로 찾아내기 어려워야 한다는 암호학적 해시 함수의 중요한 성질이므로 옳다.
    3. 역상 저항성은 주어진 해시값에 대해 그 값을 만들어 내는 원래 입력을 현실적으로 찾아내기 어려워야 한다는 해시 함수의 성질이므로 옳다.
    4. 제2 역상 저항성은 특정 입력이 주어졌을 때 그 입력과 같은 해시값을 만드는 다른 입력을 현실적으로 찾기 어려워야 한다는 성질이므로 옳다.
    🧮 풀이
    1. 甲이 비밀번호의 해시값만 저장된 데이터베이스를 확보해 해시 연산을 거꾸로 실행하여 원래 비밀번호를 바로 복원하려 했지만, 해시 함수에는 일반적인 역변환 절차가 없었다.
    2. 甲이 서로 다른 두 문서를 계속 만들어 같은 해시값을 갖는 조합을 찾으려 했지만 안전한 해시 함수에서는 그런 두 입력을 현실적인 계산량으로 발견하기가 매우 어려웠다.
    3. 甲이 특정 해시값 하나를 받은 뒤 그 값을 출력하는 원래 메시지를 찾아내려고 수많은 입력을 시험했지만, 안전한 해시 함수에서는 대응 입력을 현실적으로 찾기 어려웠다.
    4. 甲이 이미 정해진 계약서 한 장을 받은 뒤 내용이 다른 문서 중 같은 해시값을 갖는 것을 찾아 바꿔치기하려 했지만, 현실적인 계산량으로 그런 두 번째 문서를 만들지 못했다.

    암호학적 해시 함수는 일방향성을 가지며 충돌 저항성·역상 저항성·제2 역상 저항성을 갖추어야 한다.

    다음에서 설명하는 공격을 막는 방법으로 옳지 않은 것은?

    공격자가 몰래 보관해둔 기존의 정상적인 MAC(Message Authentication Code) 값을 재사용하여 전송하는 공격이다.

    1. 1. 비표(nonce) 사용
    2. 2. 리다이렉션(redirection) 사용
    3. 3. 타임스탬프(timestamp) 사용
    4. 4. 순서 번호(sequence number) 사용

    정답 2번

    🔍 보기별 해설
    1. 비표는 매번 새로운 값을 넣어 과거의 MAC(메시지 인증 코드)을 그대로 다시 보낸 메시지인지 구별할 수 있으므로 방어 방법으로 옳다.
    2. 리다이렉션은 통신이나 요청의 방향을 다른 곳으로 돌리는 방식일 뿐 과거 인증 메시지의 재사용 여부를 판별하지 못하므로 옳지 않다(정답).
    3. 타임스탬프는 메시지가 허용된 시간 범위에서 생성되었는지 검사하여 오래전에 저장한 인증값의 재전송을 거부할 수 있으므로 옳다.
    4. 순서 번호를 메시지마다 증가시키고 이미 처리한 번호를 거부하면 이전에 기록해 둔 인증 메시지를 다시 보내는 공격을 막을 수 있으므로 옳다.
    🧮 풀이
    1. 甲이 요청마다 한 번만 쓰는 비표를 발급하고 MAC(메시지 인증 코드) 계산에도 함께 넣었다. 공격자가 예전 메시지를 그대로 다시 보내자 현재 비표와 달라 서버가 즉시 거부했다.

    1. Alert Protocol은 SSL 통신에서 오류나 경고, 연결 종료 등의 상태를 상대에게 알리는 역할을 하므로 인증과 암호 알고리즘 협상을 담당하지 않아 옳지 않다.
    2. Record Protocol은 상위 데이터를 단편화하고 MAC과 암호화를 적용해 기밀성과 무결성을 제공하며, 인증과 알고리즘 협상을 직접 담당하지 않으므로 옳지 않다.
    3. Handshake Protocol은 서버와 클라이언트 인증을 수행하고 사용할 암호·MAC 알고리즘과 키 관련 정보를 협상하여 세션을 설정하므로 옳다(정답).
    4. Change Cipher Spec은 협상된 암호 명세를 이후 통신에 적용하도록 알리는 프로토콜이며, 암호와 MAC 알고리즘 자체를 협상하는 역할은 아니므로 옳지 않다.
    🧮 풀이
    1. 甲이 SSL 연결 중 서버 인증서에 문제가 생기자 Alert 메시지가 전달되어 인증 관련 오류가 통보됐고, 연결을 정상 종료할 때에도 별도의 종료 알림이 상대에게 전달됐다.
    2. 甲이 SSL로 업무 데이터를 보내자 Record Protocol이 데이터를 일정 크기로 나누고 MAC을 붙인 뒤 암호화했으며, 수신 측은 이를 복호화하고 무결성을 확인해 원래 데이터를 복원했다.
    3. 甲이 SSL 서버에 접속하자 Handshake 메시지를 주고받으며 서버 인증서를 확인하고 사용할 암호와 MAC 알고리즘을 고른 뒤, 양쪽이 세션에서 사용할 암호키를 마련했다.
    4. 甲이 SSL Handshake에서 암호 방식과 키 협상을 모두 마친 뒤 Change Cipher Spec 메시지를 보내자, 다음 Record부터 새로 협상한 암호 명세를 실제 통신에 적용하기 시작했다.

    SSLv3에서 상호 인증과 암호·MAC 알고리즘 및 키 협상을 담당하는 것은 Handshake Protocol이다.

    1. Basic Constraints(기본 제약) 확장은 인증서 주체가 CA(인증 기관) 역할을 할 수 있는지와 인증 경로 길이 제한 등을 나타내므로 옳다.
    2. Authority Key Identifier(기관 키 식별자)는 인증서 서명 검증에 필요한 발급자의 공개 키를 식별하도록 돕는 확장 필드이므로 옳다.
    3. Key Usage(키 용도)는 해당 공개 키가 전자서명, 키 암호화, 인증서 서명 등 어떤 목적으로 사용될 수 있는지를 제한하여 나타내므로 옳다.
    4. Subject Alternative Name(주체 대체 이름)은 발급자가 아니라 인증서 주체의 도메인이나 전자우편 주소 등 대체 이름을 담으므로 옳지 않다(정답).
    🧮 풀이
    1. 甲이 서버 인증서를 검사하다 Basic Constraints(기본 제약) 항목에서 CA(인증 기관) 여부를 확인했다. 일반 서버 인증서에는 인증 기관 역할이 허용되지 않은 것으로 표시되어 다른 인증서에 서명할 수 없음을 확인했다.
    2. 甲이 발급받은 서버 인증서의 발급자 정보가 맞는지 의심스러워 체인 상위 기관의 인증서를 하나씩 열어 보았다. 발급자 인증서에 적힌 키 정보와 대조해 서명 검증에 쓸 공개 키가 무엇인지를 가려냈다.
    3. 甲이 인증서의 Key Usage(키 용도) 항목을 열어 전자서명과 키 암호화 허용 여부를 살폈다. 인증서 서명 권한은 표시되지 않은 것을 확인하고 해당 키를 다른 인증서 발급에 사용하지 않도록 설정했다.
    4. 甲이 웹 서버 인증서의 Subject Alternative Name(주체 대체 이름)을 확인하자 여러 도메인 이름이 나열되어 있었다. 접속한 주소가 그 목록에 있는지 대조하여 인증서가 해당 서버 이름을 보호하는지 확인했다.

    X.509 버전 3의 Subject Alternative Name(주체 대체 이름)은 발급자가 아니라 인증서 주체의 여러 대체 이름을 나타낸다.
