    다음과 같이 접근 시간이 주어졌을 때, 캐시 적중률은? (단, 캐시 적재 시간과 캐시 적중 여부 검사 시간은 제외한다)

    ○ 평균 기억장치 접근 시간 ＝ 2.5 ms

    ○ 주기억 장치 접근 시간 ＝ 11.5 ms

    ○ 캐시 기억장치 접근 시간 ＝ 1.5 ms

    1. 1. 0.8
    2. 2. 0.85
    3. 3. 0.9
    4. 4. 0.95

    정답 3번

    🔍 보기별 해설
    1. 적중률을 h로 두면 2.5=1.5h+11.5(1−h)=11.5−10h이다. 10h=9이므로 h=0.9가 옳다(정답).
    🧮 풀이
    1. ① 캐시에 자료가 있으면 1.5밀리초, 없으면 주기억장치에서 11.5밀리초가 든다. 적중 비율을 h, 미적중 비율을 1−h로 두고 두 시간을 가중 평균한다.
    2. → 2.5=1.5h+11.5(1−h)
    3. ↓
    4. ② 괄호를 풀어 2.5=11.5−10h를 얻는다. 양변을 정리하면 10h=9다.
    5. → h=9÷10=0.9
    6. ↓
    7. ③ 적중률 0.9를 대입하면 1.5×0.9+11.5×0.1=1.35+1.15=2.5밀리초가 된다. 주어진 평균 시간과 같아 계산을 검산할 수 있다.
    8. → 적중률 0.9

    평균 접근 시간 2.5=1.5h+11.5(1−h)를 풀면 적중률 h=0.9이므로 정답은 3번이다.

    다음 그림은 TCP 기반 서버와 클라이언트 간 소켓 통신을 위한 함수 호출 관계를 나타낸다. (가) ～ (다)에 들어갈 내용을 바르게 연결한 것은?

    (가) (나) (다)

    1. 1. request( ) accept( ) 연결 종료 요청
    2. 2. accept( ) connect( ) 연결 종료 요청
    3. 3. listen( ) accept( ) 데이터 송수신
    4. 4. request( ) connect( ) 데이터 송수신

    정답 3번

    🔍 보기별 해설
    1. request()는 그림의 서버 소켓 호출 순서에 들어갈 표준 함수가 아니다. 마지막 칸도 연결 종료 요청이 아니라 데이터 송수신 단계이므로 옳지 않다.
    2. accept()는 서버가 연결 요청을 받아들이는 함수지만 첫 칸의 대기 설정에는 listen()이 온다. connect()는 클라이언트가 연결을 시작할 때 쓰므로 옳지 않다.
    3. listen()은 서버 소켓을 연결 대기 상태로 만들고 accept()는 들어온 요청을 받아들인다. 연결 후 데이터를 송수신하므로 옳다(정답).
    4. request()는 서버 소켓의 대기 설정 함수가 아니고 connect()는 클라이언트 쪽 호출이다. 그림의 서버 호출 순서와 맞지 않으므로 옳지 않다.
    🧮 풀이
    1. 서버가 socket을 만들고 주소를 bind한 다음 접속을 기다린다. 이 단계에서는 listen으로 대기 상태를 설정해야 한다. request를 넣으면 서버의 호출 흐름이 성립하지 않고 연결 뒤의 데이터 교환 단계도 빠진다.
    2. 클라이언트는 서버에 접속하려고 connect를 호출한다. 서버는 listen으로 대기하다가 accept로 그 요청을 받아들인다. 클라이언트 함수를 서버의 다음 단계에 넣으면 양쪽 역할이 뒤섞인다.
    3. 채팅 서버가 소켓을 만들고 포트에 bind한 뒤 listen으로 연결을 기다린다. 사용자가 접속하면 서버가 accept를 호출해 연결을 확정한다. 이후 양쪽 소켓에서 read와 write로 메시지를 주고받는다.
    4. 서버의 첫 연결 대기 단계에 request를 넣고 다음에 connect를 두면 호출 주체가 맞지 않는다. 접속 요청은 클라이언트가 connect로 시작한다. 서버 쪽에서는 listen과 accept가 순서대로 필요하다.

    서버는 listen 뒤 accept로 연결을 받아들이고 이어 데이터를 송수신하므로 정답은 3번이다.

    프로세스 간 통신에 대한 설명으로 옳지 않은 것은?

    1. 1. 파이프(pipe)는 두 프로세스가 통신할 수 있게 하는 전달자로서 동작한다.
    2. 2. 지명 파이프(named pipe)는 서로 통신하는 프로세스 간 부모－자식 관계가 반드시 필요하다.
    3. 3. 신호(signal)는 알려 줄 사건의 근원지나 이유에 따라 비동기식으로도 전달될 수 있다.
    4. 4. 공유 메모리를 사용하는 프로세스 간 통신에서 프로세스들은 동시에 동일한 위치에 쓰지 않도록 책임져야 한다.

    정답 2번

    🔍 보기별 해설
    1. 파이프는 한 프로세스가 쓴 데이터를 다른 프로세스가 읽게 하는 통신 경로다. 프로세스 사이의 전달자로 작동하므로 옳다.
    2. 지명 파이프는 파일 시스템에 이름이 있어 서로 관계없는 프로세스도 같은 이름으로 열 수 있다. 부모·자식 관계가 필수라는 설명은 옳지 않다(정답).
    3. 신호는 특정 사건의 발생을 프로세스에 비동기적으로 알릴 수 있다. 사건의 이유에 따라 전달될 수 있으므로 옳다.
    4. 공유 메모리의 같은 위치에 여러 프로세스가 동시에 쓰면 데이터 경합이 생긴다. 접근 순서를 조정할 책임이 있으므로 옳다.
    🧮 풀이
    1. 프로세스 A의 출력이 파이프를 거쳐 프로세스 B의 입력으로 들어간다. B는 A가 쓴 바이트를 차례로 읽어 처리한다. 파이프가 두 프로세스 사이에 데이터 경로를 제공한다.
    2. 서로 독립적으로 실행된 두 프로그램이 파일 시스템에 만들어 둔 지명 파이프를 연다. 한쪽이 기록한 데이터를 다른 쪽이 읽는다. 두 프로그램이 부모·자식으로 생성되지 않았어도 같은 이름을 통해 통신할 수 있다.
    3. 자식 프로세스가 종료되면 운영체제가 부모에게 신호를 보내 상태 변화를 알린다. 부모가 그 시점에 다른 작업 중이어도 신호가 전달될 수 있다. 사건 발생에 맞춘 비동기 통지의 예다.
    4. 프로세스 둘이 공유 메모리의 재고 수량을 동시에 바꾸면 한쪽의 갱신이 사라질 수 있다. 잠금이나 다른 동기화 수단으로 같은 위치의 쓰기 순서를 조정한다. 공유 공간을 쓰는 프로그램이 직접 경합을 막아야 한다.

    지명 파이프는 부모·자식이 아닌 프로세스 사이에서도 쓸 수 있으므로 정답은 2번이다.

    파이프라이닝 기법에 대한 설명으로 옳지 않은 것은?

    1. 1. 데이터 해저드는 앞의 명령 결과가 다음 명령의 입력으로 사용될 때 발생한다.
    2. 2. 이론적으로는 파이프라인의 단계 수만큼 빨라지지만, 이것을 방해하는 요소인 해저드가 발생할 수 있다.
    3. 3. 파이프라이닝은 명령어 하나를 여러 단계로 나누어 각각을 독립적인 장치에서 동시에 실행하는 기법이다.
    4. 4. 제어 해저드는 서로 다른 단계에서 실행되는 명령이 컴퓨터 내의 장치 하나를 동시에 사용하려고 할 때 발생한다.

    정답 4번

    🔍 보기별 해설
    1. 데이터 해저드는 앞 명령의 결과가 준비되기 전에 뒤 명령이 그 값을 필요로 할 때 생긴다. 결과 의존을 설명하므로 옳다.
    2. 단계가 겹치면 이상적으로 처리량이 늘지만 해저드가 진행을 막을 수 있다. 이론적 속도 향상과 실제 제약을 함께 설명하므로 옳다.
    3. 파이프라이닝은 명령 실행을 여러 단계로 나눠 서로 다른 명령의 단계를 동시에 진행한다. 독립 장치를 활용한 겹침이므로 옳다.
    4. 동일한 하드웨어 자원을 두 단계가 함께 쓰려는 경우는 구조적 해저드다. 분기 결과에 따라 다음 명령이 달라지는 제어 해저드가 아니므로 옳지 않다(정답).
    🧮 풀이
    1. 덧셈 명령이 레지스터 R1에 결과를 써야 뒤의 곱셈 명령이 R1을 읽을 수 있다. 곱셈이 값을 너무 일찍 요구하면 기다리거나 전달 경로를 사용해야 한다. 앞선 결과에 의존하는 데이터 해저드다.
    2. 파이프라인이 다섯 단계면 여러 명령의 단계를 겹쳐 처리할 수 있다. 분기나 자료 의존이 생기면 일부 단계를 멈추거나 비워야 한다. 그래서 실제 성능이 이상적인 단계 수만큼 늘지는 않는다.
    3. 명령 A가 실행 단계에 있을 때 명령 B는 해독 단계, 명령 C는 인출 단계에 있다. 서로 다른 명령을 각기 다른 단계에서 한꺼번에 처리한다. 한 명령 전체를 같은 시점에 여러 장치가 모두 끝낸다는 뜻은 아니다.
    4. 명령어 인출과 데이터 읽기가 같은 메모리 포트를 동시에 요구한다. 포트가 하나뿐이면 두 단계 중 하나를 기다리게 해야 한다. 자원 충돌은 구조적 해저드이며 분기 방향을 몰라 생기는 문제는 제어 해저드다.

    장치 하나를 동시에 사용하려는 경우는 구조적 해저드이며 제어 해저드가 아니므로 정답은 4번이다.

    원형 연결 리스트에 대한 설명으로 옳은 것은?

    1. 1. 하나의 노드에서 모든 노드로의 접근이 가능하다.
    2. 2. 하나의 노드에서 링크를 계속 따라가면 모든 노드를 거쳐도 자기 자신으로 되돌아올 수 없다.
    3. 3. 마지막 노드의 링크 필드 값은 NULL이다.
    4. 4. 리스트의 끝에 노드를 삽입하는 연산이 단순 연결 리스트보다 비효율적이다.

    정답 1번

    🔍 보기별 해설
    1. 원형 연결 리스트의 마지막 노드는 다시 첫 노드를 가리킨다. 한 노드에서 링크를 계속 따라가면 모든 노드에 접근할 수 있으므로 옳다(정답).
    2. 링크를 계속 따라가면 마지막 노드 뒤에 다시 시작 노드가 나온다. 자기 자신으로 돌아올 수 없다는 설명은 옳지 않다.
    3. 원형 연결 리스트에서는 마지막 노드의 링크가 첫 노드를 가리킨다. 끝의 링크가 NULL이라는 설명은 옳지 않다.
    4. 끝 노드를 가리키는 포인터를 관리하면 마지막 노드 뒤에 새 노드를 연결하기 쉽다. 끝 삽입이 반드시 더 비효율적이라는 단정은 옳지 않다.
    🧮 풀이
    1. 노드 A가 B를, B가 C를, C가 다시 A를 가리킨다. A에서 링크를 따라가면 B와 C를 거쳐 A로 돌아온다. 출발 위치가 어디여도 이 고리 안의 모든 노드를 방문할 수 있다.
    2. 노드 B에서 시작해 C, A 순서로 이동한다. 다음 링크는 다시 B를 가리킨다. 원형 구조에서는 계속 따라갈 때 출발 노드가 재등장한다.
    3. 마지막 노드 C의 링크가 NULL이면 그곳에서 탐색이 끝나는 일반 단순 연결 리스트가 된다. 원형으로 만들려면 C가 첫 노드 A를 가리켜야 한다. 마지막 링크의 대상이 두 구조를 구분한다.
    4. 끝 노드 포인터를 가지고 있는 원형 리스트에 새 노드 D를 추가한다. D가 첫 노드를 가리키게 하고 기존 끝 노드가 D를 가리키도록 바꾼다. 포인터 관리 방식에 따라 끝 삽입을 효율적으로 할 수 있다.

    원형 연결 리스트는 링크를 따라가면 모든 노드를 거쳐 출발 노드로 돌아오므로 정답은 1번이다.

    다음 파이썬(Python) 프로그램의 출력 결과는?

    a = [1, 3, 5, 7] b = {1, 3, 5, 7} c = (1, 3, 5, 7) a.append(3) b.add(3) print(len(a) + len(b) + len(c))

    1. 1. 10
    2. 2. 12
    3. 3. 13
    4. 4. 14

    정답 3번

    🔍 보기별 해설
    1. a의 길이는 5, b의 길이는 4, c의 길이는 4다. len(a)+len(b)+len(c)=5+4+4=13이므로 옳다(정답).
    🧮 풀이
    1. ① a는 네 원소가 있는 리스트다. append(3)을 실행하면 기존의 3과 별개로 3이 끝에 추가돼 다섯 원소가 된다.
    2. → len(a)=5
    3. ↓
    4. ② b는 집합이므로 이미 있는 3을 add(3)으로 다시 넣어도 네 원소 그대로다. c는 네 원소가 있는 튜플이며 변경 명령이 없다.
    5. → len(b)=4, len(c)=4
    6. ↓
    7. ③ 마지막 print는 세 길이를 순서대로 더한다. 리스트에서만 원소 수가 늘어난 사실을 반영한다.
    8. → 5+4+4=13

    리스트는 중복값이 추가돼 5개, 집합과 튜플은 각각 4개라 합계 13이므로 정답은 3번이다.

    2. 2. 오버플로
    3. 3. 전원 이상
    4. 4. 기계 오작동

    🔍 보기별 해설

    NoSQL의 특징으로 옳지 않은 것은?

    1. 1. 동적 스키마를 지원할 수 있다.
    2. 2. 다양한 형태의 비정형 데이터들도 다룬다.
    3. 3. 빠른 속도로 증가하는 대용량 데이터를 처리하는 데 적합하지 않다.
    4. 4. 관계형 데이터베이스보다는 ACID 특성을 중요시하지 않는다.

    정답 3번

    🔍 보기별 해설
    1. NoSQL(Not Only SQL, 비관계형 데이터 저장 방식을 포함하는 개념)은 자료 구조가 달라져도 동적 스키마로 수용할 수 있다. 특징에 해당하므로 옳다.
    2. NoSQL 저장소는 문서나 키·값처럼 정형 테이블에 맞추기 어려운 자료도 다룬다. 비정형 데이터 지원이므로 옳다.
    3. NoSQL은 분산 확장 등을 통해 빠르게 증가하는 큰 데이터 규모를 처리하도록 설계된 경우가 많다. 적합하지 않다는 설명은 옳지 않다(정답).
    4. 관계형 데이터베이스는 트랜잭션의 ACID(Atomicity, Consistency, Isolation, Durability) 성질을 강조한다. NoSQL은 모델에 따라 이를 완화하거나 다른 방식으로 보장하므로 일반적인 비교로 옳다.
    🧮 풀이
    1. 문서 데이터베이스에 사용자의 기본 정보와 선택 항목을 저장한다. 어떤 문서에는 관심 분야가 있고 다른 문서에는 없어도 같은 저장소에 넣을 수 있다. 고정 열 목록만 고집하지 않는 동적 스키마 사례다.
    2. 웹 게시글 본문, 태그 목록, 첨부 정보는 글마다 구조가 달라질 수 있다. 문서 형태로 통째 저장하면 모든 글을 동일한 표의 열에 맞출 필요가 줄어든다. 다양한 형태의 자료를 다루는 사례다.
    3. 접속 기록이 하루에 수억 건씩 늘어나는 서비스를 운영한다. 데이터를 여러 서버에 나눠 저장하고 조회 부하를 분산하는 NoSQL 구조를 선택할 수 있다. 대규모·고속 증가 데이터에 맞지 않는다는 단정과 어긋난다.
    4. 은행 잔액 이체는 여러 변경이 함께 성공하거나 실패해야 하므로 강한 트랜잭션 보장이 중요하다. 로그 분석용 저장소는 분산 성능과 유연성을 더 우선할 수 있다. NoSQL 제품마다 보장 수준이 달라 특정 성질을 모두 포기한다는 뜻은 아니다.

    NoSQL은 큰 규모로 빠르게 늘어나는 데이터를 다루기 위해 쓰이므로 정답은 3번이다.

    🔍 보기별 해설

    2. 응급실에서 긴급도가 가장 높은 환자를 먼저 처리하려고 대기 항목에 우선순위를 붙인다. 힙에 항목을 넣으면 가장 높은 우선순위가 위로 올라온다. 우선순위 큐를 힙으로 구현한 사례다.
    3. 힙에 노드를 차례로 추가할 때 마지막 층의 빈자리를 왼쪽부터 채운다. 중간 층을 비워 두고 더 아래층을 만드는 형태는 허용하지 않는다. 이 형태를 완전 이진 트리라고 한다.

    이진 힙의 삽입은 위로 재정렬할 수 있어 O(log n)이므로 정답은 1번이다.
